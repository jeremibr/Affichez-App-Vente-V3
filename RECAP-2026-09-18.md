# What changed on 2026-09-18

One day, 21 merged PRs. Written for whoever picks this up next.

It started as *"the sales report stopped updating in real time"* and turned into a
full audit of every number the dashboard shows. Deep detail and evidence live in
**[STATS-INTEGRITY.md](STATS-INTEGRITY.md)**; this is the plain version.

---

## 1. The three things most likely to surprise you

### `sales` now holds EVERY quote, not just the won ones

It went **8,088 → 16,261 rows**. Drafts, sent, expired and declined quotes are all
in there now. Any query that counts or sums `sales` has to say which statuses it
means:

```sql
WHERE status IN ('accepted','invoiced')     -- revenue
```

**Never `!= 'declined'`.** That used to be the same thing, because the table only
had three statuses and every row was a winner. It now silently includes ~8,000
quotes nobody ever won. Every existing revenue query was converted before the data
landed — if you add a new one, this is the trap.

### `sale_date` and `quote_date` answer different questions

| column | meaning | use it for |
| --- | --- | --- |
| `sale_date` | when the money happened (acceptance date, falling back to issue date) | revenue |
| `quote_date` | when the quote was **issued** | closing rates, activity |
| `accepted_date` | acceptance date, `NULL` if never accepted | "was this ever won" |

"Of the quotes we sent in March, how many did we win" is a **cohort** question and
must group by `quote_date`. "What did we bill in March" groups by `sale_date`.
Mixing them was the single most common defect found today — it appeared three
separate times.

### Any function called without a login must be pinned in `config.toml`

```toml
[functions.my-function]
verify_jwt = false
```

Miss it and the function returns **401 to its caller with nothing logged**. That
is what took the quotes sync down for 22 hours on 2026-08-24: a routine redeploy
applied `config.toml`, which had no entry for `zoho-sync`, so `verify_jwt` reverted
to `true` and every pg_cron tick was rejected at the gateway before the function
ran. No error, no log, the dashboard just stopped.

All **11** such functions are now pinned, including the two n8n calls
(`weekly-sales-report`, `weekly-mandates-report`) which were still unpinned as of
this morning.

## 2. What was actually wrong

| area | was | now |
| --- | --- | --- |
| **Closing rate** (Créé par) | **92%** | **48%** |
| Office % of target | QC read 46% | "—" |
| Rep-group target ("Interne") | measured against the full team target | "—" |
| YoY 2025 | last year = **$0** | real 2024 figures |
| Tâches dates | counted in **UTC** | Montréal |
| Tâches completion rate | could exceed 100%, capped at 100 in the UI | two separate honest numbers |
| Tâches week-over-week | partial week vs whole week | same elapsed slice |
| Nb factures | KPI card and table disagreed | both exclude credit notes |
| Anon API access | **read AND write** on 38 objects | revoked |
| CI deploys | failing silently since Sept 3 | working |

### The closing rate, in detail

`win_rate` was `quotes_won ÷ quotes_created`, where `quotes_created` was *every row
in `sales`* — and every row in `sales` was a quote that had already been won. The
page read 92% because it was dividing winners by winners.

Verified against the Zoho API: the QC org alone holds 3,000+ expired and 1,500+
declined quotes the database had never seen. Real figure for quotes issued in
2026: **1,683 won of 3,507 sent = 48.0%**.

The denominator is *quotes actually sent* — `sent, accepted, invoiced, declined,
expired`. **Drafts are excluded** (stored and visible, but a draft was never shown
to a client, so counting it as a lost opportunity punishes work-in-progress).

### Why revenue never moved

`5,987,557 / 71.0%` before and after adding 8,000 non-won quotes. That was
sequenced deliberately:

1. Make all 18 revenue objects say `IN ('accepted','invoiced')` — a **provable
   no-op** while only three statuses existed, verified on real data (both
   predicates selected exactly 7,901 of 8,086 rows).
2. *Then* add the schema and backfill the data.

Doing it the other way round would have inflated every figure on every page.
7 of those 18 objects were **views**, which are in no migration — they were only
findable because of the schema snapshot.

## 3. Security

`anon` — the key shipped inside the public JS bundle — held
`DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE` on **all 38
objects**, not just SELECT. Seven tables had no RLS at all, so on those the grant
was live and unguarded to anyone with the site URL:

```
paye_entries (payroll) · rep_objectives · objectives_factures
excluded_clients · excluded_reps · paye_meta · sync_state
```

**Fixed by revoking the schema from `anon`**, not by adding more policies, for two
reasons RLS could never have covered:

- **8 of 13 views run with owner rights**, so base-table RLS doesn't reach them.
  `invoices` correctly returned zero rows to anon while `v_inv_weekly_summary`
  served **4,270 rows of the same data** — the Sept 3 lockdown had been bypassed
  from the day it shipped.
- **`zoho_service_labels` is a materialized view.** Those support no RLS at all.

A privilege check runs *before* any policy, so one revoke closed tables, views and
matviews together. RLS still went on the seven unprotected tables as a second
layer.

## 4. The left sidebar was restructured

Separate from the stats work — `c49c484`, *"file screens by subject, not by
permission"*.

**The problem:** `Administration` meant both "settings" and "admin-only", so every
restricted screen was filed there regardless of what it was actually about.

**Now a section says what a screen is about; a permission decides who sees it.**

| section | screens |
| --- | --- |
| **Ventes Affichez** | Devis, Factures, Comptes, Publicité |
| **Notre équipe** | Tâches CRM, Commissions, Objectifs d'équipe |
| **Administration** | Documents créés, then the three settings screens |

Other changes in it:

- **Publicité moved out of the Comptes module** to `/publicite`. `getSectionKey`
  files by path prefix, so the old URL made the page a child of Comptes. **A
  redirect keeps bookmarked and pasted links working**, query string included.
- **"Créé par" is renamed "Documents créés"** and deliberately stays in
  Administration — it's the owner's own back-office view. CLAUDE.md records that
  so it doesn't get moved back.
- **Empty sections no longer render.** A module with no visible screens, and a
  section with no visible modules, are hidden — so a rep now sees two sections
  rather than four plus an empty chevron.
- **Admin-only entries hide while an admin previews a rep's view**, following the
  rule Administration already used.

## 6. Ops notes

- **Backfill is done.** `QUOTES_STORE_ALL_STATUSES=true` is set; the 5-minute cron
  maintains every status from here.
- **`zoho-quote-creator-sync` is still catching up** (~6,000 quotes pending, runs
  every 3 min). Until it finishes the Créé par Taux reads high, because the page
  only shows quotes whose creator is resolved. It self-corrects.
  `get_quote_creator_link_status()` reports progress.
- **A full sync runs in slices.** Zoho's estimates API has **no working date
  filter** — `date_start` and `date_after` are both accepted and silently ignored
  (asking for 2026-09-01 onward returns a 2015 record). So a full walk can't be
  narrowed and doesn't fit in one 150s invocation. It resumes from a cursor in
  `sync_state.cursor_token`, ordered `created_time` ascending so pages stay stable
  between slices.
- **Orphan sweeping needs `x-orphan-sweep: true`** — a won-only walk that finishes
  in one pass. A sliced walk can never sweep (the seen-id set doesn't survive
  across invocations) and correctly refuses to try.
- **`supabase/schema.sql`** is a snapshot of the live schema. It went stale within
  an hour of being taken. Regenerate before relying on it:
  `supabase db dump -s public -f supabase/schema.sql` (needs Docker).

## 8. The one rule worth keeping

Every defect found today was the same shape: **a number computed over a population
that wasn't what its name suggested.**

Before writing any ratio, run a `GROUP BY` on the source table and confirm that
what you're dividing by is actually in there. The losers are usually missing.

And **verify against the source, not the mirror.** Twice today an inference from
the database looked obviously right and was wrong — including a "delete these 4
orphans" that would have destroyed two legitimate quotes, because `quote_date IS
NULL` meant "skipped by the backfill cutoff" as well as "deleted from Zoho".
Checking each one against the Zoho API took two minutes and changed the answer.
