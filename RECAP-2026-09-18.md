# What changed on 2026-09-18 — read this before touching stats

One day's work, 20 merged PRs. Short version for whoever picks this up next.
Deep detail lives in **[STATS-INTEGRITY.md](STATS-INTEGRITY.md)**.

---

## The three things that will surprise you

**1. `sales` now holds EVERY quote, not just won ones.**
It went 8,088 → 16,261 rows. Drafts, sent, expired and declined quotes are in
there now. Any query that counts or sums `sales` must say which statuses it
means:

```sql
WHERE status IN ('accepted','invoiced')   -- revenue
```

Never `!= 'declined'` — that now includes 8,000 quotes nobody ever won.

**2. Two different dates, and they mean different things.**

| column | meaning |
| --- | --- |
| `sale_date` | when the money happened (acceptance date) |
| `quote_date` | when the quote was **issued** |

Revenue groups by `sale_date`. Closing rates group by `quote_date`, because
"of the quotes we sent in March, how many did we win" is a different question
from "what did we bill in March".

**3. Any function called without a login must be pinned in `config.toml`.**

```toml
[functions.my-function]
verify_jwt = false
```

Miss this and the function silently returns 401 to its caller. That is what took
the quotes sync down for 22 hours in August: nothing errored, nothing logged, the
dashboard just stopped updating. All 11 such functions are now pinned.

## What was actually wrong

| | was | now |
| --- | --- | --- |
| Closing rate (Créé par) | **92%** | **48%** — it was dividing winners by winners |
| Office % of target | QC read 46% | "—" — targets are company-wide, there is no per-office target |
| YoY 2025 | last year = **$0** | real — `fiscal_quarters` had no 2024 rows |
| Tâches dates | counted in **UTC** | Montréal — evening tasks were landing on the next day |
| Tâches completion rate | could exceed 100%, capped in the UI | two honest numbers: cohort + throughput |
| Nb factures | card and table disagreed | both exclude credit notes |
| Anon access | **full read AND write** on 38 objects incl. payroll | revoked |
| CI deploys | failing silently since Sept 3 | working |

**Revenue never moved through any of it**: `5,987,557 / 71.0%` before and after.
That was deliberate — the revenue filters were made explicit *first*, as a
provable no-op, so adding 8,000 non-won quotes couldn't inflate anything.

## Security, in case it matters to you

`anon` — the key shipped in the public JS bundle — held
`DELETE, INSERT, TRUNCATE, UPDATE` on all 38 objects, not just SELECT. Seven
tables had no RLS at all, including `paye_entries` (payroll). Revoked schema-wide.

Also: 8 of 13 views ran with owner rights, so they bypassed the RLS added to
`invoices` back on Sept 3 — `v_inv_weekly_summary` had been serving 4,270 rows of
"protected" invoice data ever since.

  filter, so a full walk can't finish in one 150s invocation. It resumes from a
  cursor in `sync_state.cursor_token`.

  sliced walk can never sweep, and refuses to try.

  regenerate before relying on it.

## The one rule worth keeping

Every defect found today was the same shape: **a number computed over a
population that wasn't what its name suggested.** Before writing any ratio, run a
`GROUP BY` on the source table and check that what you're dividing by is actually
in there. The losers are usually missing.
